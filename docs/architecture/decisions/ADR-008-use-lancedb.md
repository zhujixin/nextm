# ADR-008: 使用 LanceDB 作为本地向量搜索

**日期**: 2026-05-22

**状态**: 已接受

---

## 背景

NextM 需要向量搜索能力支持语义搜索和 AI 推荐。本地离线场景需要一个嵌入式的向量数据库。

## 选项

| 方案 | 优点 | 缺点 |
|------|------|------|
| **LanceDB** | 嵌入式无服务端、Go SDK 原生 | 项目较新、生态较小 |
| **Qdrant** | 成熟、功能丰富 | 需要独立服务进程、不适合本地优先 |
| **Milvus** | 大规模场景、分布式 | 重、运维复杂、不适合单机场景 |
| **SQLite + 自制向量索引** | 零新依赖 | 实现复杂、性能有上限 |

## 决策

本地使用 **LanceDB Go SDK**，云端使用 **pgvector**。

## 理由

1. **嵌入式** — 无独立服务进程，嵌入 Go 应用进程中运行
2. **Go SDK** — 原生 Go 绑定，无需 HTTP 调用或额外客户端
3. **列式存储** — 高效读取 embedding 向量 + 元数据属性
4. **本地优先** — 数据存储在本地文件系统，离线可用
5. **云端互补** — pgvector 在云端提供一致能力的向量搜索

## 影响

- LanceDB 数据目录存储在本地应用数据目录
- 向量维度统一为 768（与 embeddings 模型输出对齐）
- 语义搜索在本地走 LanceDB，云端走 pgvector，通过 `DBSelector` 切换
- 首次搜索需要构建索引，可能有几秒冷启动延迟
