# ADR-006: 使用 Asynq 作为后台任务队列

**日期**: 2026-05-22

**状态**: 已接受

---

## 背景

NextM 需要后台任务队列处理异步操作：OCR 处理、AI 推理、数据导出、智能体定时任务等。

## 选项

| 方案 | 优点 | 缺点 |
|------|------|------|
| **Asynq** | Redis 后端无额外依赖、延迟任务、Go 原生 | 强依赖 Redis |
| **Machinery** | 支持多种后端（Redis/AMQP/MongoDB） | 维护不活跃、社区较小 |
| **自建 (goroutine + channel)** | 零依赖、完全控制 | 无持久化、无延迟调度、无重试机制 |

## 决策

选择 **Asynq**（Redis 后端）。

## 理由

1. **无额外依赖** — 使用已有 Redis 实例，无需部署新服务
2. **延迟任务** — 原生支持 `ProcessIn()` / `ProcessAt()`，适合定时智能体
3. **重试机制** — 内置失败重试和指数退避，默认重试 3 次
4. **任务类型安全** — 基于 Go 类型注册，编译期可见
5. **监控面板** — Asynq 提供 Web UI 监控队列状态

## 影响

- 需要 Redis 实例（可与缓存共用）
- Worker 进程 `cmd/worker` 负责消费队列
- 任务注册采用集中式任务映射表
- 监控面板可在开发环境启用
