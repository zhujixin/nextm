# ADR-002: 使用 CRDT (Yrs) 作为同步引擎

**日期**: 2026-05-22

**状态**: 已接受

---

## 背景

NextM 需要多设备数据同步能力，支持离线编辑、冲突解决和无服务器架构。

## 选项

| 方案 | 优点 | 缺点 |
|------|------|------|
| **CRDT (Yrs)** | 去中心化、无冲突合并、离线友好、实时协作 | 实现复杂、需要 CGo FFI、存储开销 |
| **OT (Operational Transform)** | 成熟（Google Docs）、实时性好 | 中心化架构、复杂度随并发增加 |
| **Last-Write-Wins (版本向量)** | 实现简单 | 数据丢失风险、不适合协作编辑 |
| **自定义同步协议** | 完全控制 | 开发成本极高、难以验证正确性 |

## 决策

选择 **Yrs (Y-CRDT)** 作为同步引擎核心，通过 CGo FFI 或纯 Go 实现集成。

## 理由

1. **离线优先** — CRDT 天然支持离线编辑，无需中心服务器协调
2. **冲突解决** — 自动合并，不会丢失任何写入（相较 LWW 的关键优势）
3. **去中心化** — 支持 P2P 同步、局域网同步，不依赖云端
4. **成熟度** — Yrs 是 Y-CRDT 的 Rust 实现，社区广泛使用（AFFiNE、Mozilla）
5. **块级协作** — 支持块级别（Block）的细粒度协作

## 影响

- 新增 Yrs 依赖（Rust → C ABI → Go FFI，或寻找纯 Go CRDT 实现）
- 本地 SQLite 中增加 CRDT change log 表
- 同步带宽可能高于 LWW 方案（需传输操作日志）
- 需要处理 GC（墓碑清理）策略
- Yrs 的 Rust 原生实现可能在 Windows 上需要额外的 CGo 工具链配置

## 备选考虑

评估过程中也考虑了纯 Go 实现 CRDT（自研），但鉴于 CRDT 的正确性验证极为复杂且 Yrs 已经过生产验证，直接绑定 Yrs 的成本远低于自研。
