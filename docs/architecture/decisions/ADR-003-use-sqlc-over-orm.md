# ADR-003: 使用 SQLc 而非 ORM

**日期**: 2026-05-22

**状态**: 已接受

---

## 背景

NextM 需要数据库访问层。需要决定使用 ORM（如 GORM、Ent）还是 SQL 代码生成工具。

## 选项

| 方案 | 优点 | 缺点 |
|------|------|------|
| **SQLc** | 类型安全、零运行时、SQL 直接控制、生成代码可读 | 需要维护 SQL 文件、不自动生成 CRUD |
| **GORM** | 上手快、自动迁移、关联预加载 | 反射开销、黑盒行为、N+1 隐患、迁移不可控 |
| **Ent** | 类型安全、图遍历查询、代码生成 | 学习曲线陡、生成代码体积大、灵活度受限 |
| **database/sql** | 零依赖、完全控制 | 样板代码多、无类型安全、易出错 |

## 决策

选择 **SQLc** 作为数据库访问层工具。

## 理由

1. **类型安全** — 编译时生成 Go 类型，SQL 错误在编译期暴露
2. **零运行时** — 生成的是纯 `database/sql` 代码，无额外开销
3. **SQL 可见性** — 所有查询以 SQL 形式版本管理，DBA 友好
4. **迁移可控** — 配合 golang-migrate 管理 DDL，避免 ORM 自动迁移的意外
5. **性能** — 手写 SQL 在所有 ORM 方案中上限最高

## 影响

- SQL 文件存放在 `internal/repository/db/queries/`
- 查询方法调用前需运行 `sqlc generate` → `make sqlc-gen`
- 复杂分页、递归查询等不易用 ORM 表达的场景，SQLc 天然支持
- 团队需掌握 SQL 编写能力（但这是技能资产而非负债）
- SQLc 不处理迁移，需配合 golang-migrate
